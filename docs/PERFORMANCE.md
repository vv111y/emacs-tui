# Reproducing latency measurements

[Instrumented completion stage profiles](../bench/results/2026-10-27-completion-stages/README.md)
retain all 15,120 samples across identity/absent sorters, source/bytecode and
Linux/macOS 31.1. They locate substantial restoration cost in projection/native
matching. They are not a paired speedup comparison; nested clocks overlap and
instrumentation changes timing/allocation overhead. The reports and auditor
preserve all fields, per-command quantiles, GC counters and exact provenance.


[Paired native movement measurements](../bench/results/2026-10-27-popup-movement/README.md)
now cover PR #54's retained-row reflow on Linux/macOS 31.1. Eight lossless raw
reports and an audit script preserve all 6,720 records, source provenance and
p50/p95/p99. At 10k rows the bytecode PTY movement median changes from 39.940 to
2.331 ms on Linux and 26.957 to 1.329 ms on macOS. Small-list Linux tails do not
uniformly improve; sequential shared-host measurements are not universal bounds.


The [native popup baseline](../bench/results/2026-10-27-native-popup/README.md)
retains Linux/macOS 31.1 source/bytecode profiles with 200 measured commands per
case, raw samples and qualified p50/p95/p99. It identifies expensive full popup
reflow and completion restoration without claiming an optimization yet.

The first [published navigation pair](../bench/results/2026-10-24-navigation/README.md)
includes environment/provenance, raw samples, p50/p95/p99 and allocation counters
before/after removing row reconstruction from selection movement. It covers
interpreted Emacs 29.3 and ordinary windows on one host, not universal latency.
The [query-clear pair](../bench/results/2026-10-24-query-clear/README.md) separates
native insertion from deletion and measures skipping predicates for empty terms.
Both retain every sample. The [fresh-bytecode profile](../bench/results/2026-10-24-bytecode/README.md)
adds all five workloads on one compiled-library configuration; native-code
performance remains unmeasured.
These published workloads explicitly use ordinary windows. The native popup
fixture below is a distinct workload; the beta2 terminal checks establish
behavior, not a latency baseline.
The [multi-term pair](../bench/results/2026-10-24-multiterm/README.md)
measures list/table searches after removing per-term projection work.

Run `make clean benchmark` with Python 3 and a real terminal-capable Emacs.
The driver creates its own 120x40 PTY and starts `emacs -Q -nw`; it does not
use your current Emacs session. Results, including every warmup and measured
sample, are written to `.cache/benchmark.json`. For a smaller run:

```sh
make clean benchmark BENCH_ARGS='--sizes 100 1000 --samples 100 --warmup 10'
```

Set `EMACS=/path/to/emacs` to select a runtime. To measure freshly bytecompiled
libraries using that runtime:

```sh
make benchmark BENCH_ARGS='--load-mode bytecode --sizes 1000 10000'
```

Both modes snapshot library sources into a fresh temporary directory. Bytecode
mode compiles all library files there with warnings treated as errors; it never
reuses checkout bytecode or writes compiled libraries into the source tree.
Source mode remains the default and rejects existing checkout library .elc files.
The fixture checks actual definition paths and function types for all six
libraries, so an unintended source/bytecode/native fallback fails the run.
Reports record load mode, loaded definition files, source/benchmark hashes and
hashes of the freshly generated bytecode. Library snapshots must match the
initial source hashes, and changes to original library/benchmark sources during
a run reject the result. The fixture/instrumentation remains interpreted in
both modes. Deferred native compilation is disabled; native-code performance
still needs separate measurement. Earlier published pairs used source mode.

`BENCH_ARGS` can also select
`--kinds navigate-list navigate-table`, `--output FILE`, and an explanatory
`--label`. Mode selection and loaded definitions are recorded rather than
inferred from file existence. Compilation and snapshot preparation occur outside
measured commands. Normal GC thresholds are retained and recorded; fixture setup runs GC before each workload, outside measured samples.

`--filter-prefix 'row 日本語 '` starts filter workloads with two terms that match
every fixture row, then measures native insertion/deletion of a third `x` term.
The prefix must be a single line ending in whitespace, and must match every
fixture row; the initial result count is checked before measuring. It is placed
in the actual editable field before warmups, with point at the end. The report's
`filter_fixture.prefix` records it. Other workloads ignore it. The default empty
prefix retains the original one-term/empty-query workload. For example:

```sh
make benchmark BENCH_ARGS="--load-mode bytecode --filter-prefix 'row 日本語 ' --kinds filter-list filter-table --sizes 1000 10000"
```

## Workloads and clocks

Each size (100, 1,000 and 10,000 rows by default) exercises:

| Workload | Native keyboard operation | Result |
| --- | --- | --- |
| `navigate-list` | Repeated `n` | Move selection, including scrolling and wraparound |
| `navigate-table` | Repeated `n` | Same, with two fixed-width projected columns |
| `filter-list` | Alternate `x` and DEL in an editable field | Callback locally filters the other view to 10% of rows, then restores all rows |
| `filter-table` | Same native edits | Same filtering over two columns |
| `provider-list` | Alternate `x` and DEL in an ephemeral query | 10ms debounce, provider with a deliberate 20ms timer, then replacement results |

Data has stable identities, numeric metadata, Japanese text and a combining
accent. The backend is explicitly ordinary windows to permit comparisons across
the supported Emacs versions. The native popup workloads below must be selected separately; these five
ordinary-window workloads make no claim about native child-frame latency. Filtering views use two columns
of windows; the provider uses the ephemeral query field above one result view.

The Python driver sends exactly one key and waits for an acknowledgement before
sending the next. The marker is written to the PTY **after** `redisplay t`.
It validates case/sample sequence and Emacs checks selected identities or
visible result counts, so a silently unbound key or failed filter cannot pass.

The driver starts a new session using `start_new_session`, then attaches the
controlling PTY in a fresh Python interpreter before executing Emacs. It does
not run Python via `preexec_fn` after fork. Stage messages are flushed outside
measured commands. This addresses a process-launch hazard while retaining the
same native key/redisplay protocol. Repeated macOS 31.1 CI stalls in the older
driver were not captured with a stack trace, so the exact blocked call is
unknown; successful checks must verify this change rather than assuming a cause.
The new stage logs subsequently located both macOS failures in Python 3.15's
post-protocol timed process wait, including after group termination. The driver
now drains terminal output and polls process status through exit, as the existing
TTY smoke runner does. This avoids both a blocked terminal writer and dependence
on platform timed-wait notifications. It does not establish which caused the
observed stall. Regressions exercise a 2 MiB terminal tail and EOF while a process
is still alive; EOF alone never counts as successful exit.

`--timeout SECONDS` covers the entire driver (default 1,800 seconds). Expiry
dumps the Python stack and fails the run; normal cleanup kills its owned process
group and waits at most five seconds. A C watchdog dumps/exits after ten extra
seconds if Python cannot dispatch the deadline. Git and CPU-model subprocesses
have ten-second limits. Unavailable Git/CPU metadata is recorded as null.
CI smoke uses a 120-second driver deadline, a five-minute outer step limit and
a 15-minute runtime-job limit, including compilation and startup. None of these
limits are performance thresholds. Published earlier pairs retain their original
versioned coordinator hashes; this hardening does not rewrite their data.

- `pty_output_ms`: Python's monotonic clock, just before writing the key through
  receipt of the acknowledgement after terminal output. Includes dispatch,
  scheduling, instrumentation, validation and PTY transport. For the provider
  case, this waits for **result** output, including debounce and provider delay.
- `command_redisplay_ms`: Emacs pre-command hook through forced redisplay in the
  post-command hook. Excludes input decoding/queueing and acknowledgement
  transport. For providers this covers immediate query/clearing display only.
- `provider_wait_ms`: Provider invocation through its timer callback, including
  the deliberately configured delay and scheduling. Not a real data-source
  benchmark and not renderer time.
- `provider_publish_redisplay_ms`: Provider callback's publishing and redisplay.
- `command_to_result_ms`: Emacs command start through result redisplay, including
  debounce, controlled provider delay and publishing.
- `cons_cells`, `string_chars`, `gc_count`, `gc_ms`: cumulative counter deltas
  over the immediate command/redisplay interval, including instrumentation.
  These are allocations, not retained heap or total bytes. Provider publishing
  occurs later and is outside these command allocation/GC counters.

This measures terminal **output**, not terminal-emulator parsing, compositor
latency, physical screen paint or human-perceived latency. There is no emulator
in this PTY fixture. Emacs elapsed clocks and Python's monotonic clock are never
subtracted from one another. Emacs timings use its elapsed wall clock, so clock
adjustments are an additional reason to retain raw data and repeat runs.

## Interpreting results

The report includes raw records, all-row/filtered-row counts, aggregate and
per-command p50/p95/p99 using nearest rank, sample counts, runtime/features,
backend, load mode and loaded definitions, actual frame geometry, requested PTY
geometry, GC settings, host/CPU,
library/benchmark source hashes and tracked Git revision/dirty state when available. Untracked
local copies report a null Git revision rather than inventing provenance.

Defaults use 10 warmups then 100 measured commands per workload. Alternating
filter/provider cases have 50 samples per command; their per-command p99 is the
maximum and is statistically weak. Use more samples for tail analysis. Repeat
before/after runs on the same otherwise idle host. CPU frequency, virtualization,
thermal state and background work are not controlled. These numbers are evidence
for finding bottlenecks, not universal performance promises.

`make clean benchmark-smoke` checks compilation, three process/PTY regressions,
all five workloads, real native input and the acknowledgement protocol in both
source and freshly bytecompiled modes, with six samples and two warmups at
100 rows. Additional source/bytecode smoke cases exercise multi-term list/table
filtering with the recorded prefix. CI runs this on each supported runtime; it has **no timing threshold**
and is not a published performance baseline. Required functional ERT/PTY tests
remain separate. Optimize only after measuring, and preserve native buffer
semantics, source identity, application effects and failure-safe updates.

## Native floating popup and completion workloads

On a terminal runtime advertising native child frames (tested by capability,
not version alone), select the native-only presentation:

```sh
make clean benchmark BENCH_ARGS='--presentation popup --sizes 100 1000 10000 --samples 200 --warmup 10 --output .cache/popup-source.json'
make benchmark BENCH_ARGS='--presentation popup --load-mode bytecode --sizes 100 1000 10000 --samples 200 --warmup 10 --output .cache/popup-bytecode.json'
```

There is no split-window substitute: unavailable native TTY child frames fail
the run without producing results. GUI execution is not measured. The default
continues to be the ordinary-window suite; mixing presentations' kinds is an
argument error. Source/bytecode snapshot and provenance rules above apply,
including the optional completion library's actual loaded definition.

| Workload | Host-buffer keyboard operation | Checked result |
| --- | --- | --- |
| `navigate-popup` | `M-n` | Next object, including scrolling/wrap, in a 48-column, 8-row popup |
| `move-popup` | `C-c C-p` | Clockwise compass position and changed actual child-frame coordinates |
| `filter-completion` | Alternate native `x` and DEL after `row ` | Actual CAPF frontend narrows to every tenth row, then restores the full matching set |

Each case starts at the center of a 120×40 parent frame. A unique candidate
text token must appear in raw terminal output before measurements; setup forces
a full redraw so previous identical screen cells cannot satisfy a new case.
Every sample asserts the original source window, buffer, frame, cursor and
surrounding text, one unchanged parent window, and the same live child. Case
cleanup checks the captured child is actually dead and completion state is
released. This does not measure a terminal emulator's or physical display's
paint time. The normal marker/identity/visible-count checks still apply.

The completion fixture uses real `completion-at-point` dispatch, `basic` style,
a synchronous table backed by a finite string list, Japanese/combining text,
and no artificial wait. The disposable source has undo recording disabled;
these timings exclude undo-history allocation. Setup and the initial CAPF invocation occur outside
samples. The table handles real metadata/boundary/completion requests. The
200-row display cap does **not** bound matching: every request can scan all
source rows. Above 2,000 rows, both filtered and unfiltered displays can contain
200 rows, while the input and provider work still change. Raw records retain
visible row counts, and every sample verifies the exact displayed candidate
values and order even when both sets hit the cap. This is a controlled provider, not an estimate for LSP,
filesystems or arbitrary installed completion packages. It does not benchmark
popup creation, acceptance, annotation, GUI fonts or async providers.

Additional raw clocks:

- `table_callback_ms` sums timed synchronous table callbacks, including their
  list matching; `table_callback_calls` records their count. It excludes CAPF
  discovery/context validation and framework work outside the table callback.
- `command_without_table_ms` subtracts that sum from `command_redisplay_ms`.
  It includes dispatch hooks, completion projection/sorting, UI work and
  instrumentation; it is **not** pure rendering time.
- `final_redisplay_ms` measures only the final forced `redisplay`, already
  included in the command total. Earlier command-driven display work can
  occur outside this subinterval.

Allocation and GC counters include the measured command's table work. Extra
clocks have overhead; compare runs with the same fixture/instrumentation.
Host invariants are checked after the Emacs command clock and before the
acknowledgement, so they contribute to `pty_output_ms`. These clocks overlap;
do not add them as independent latency components.

Use 200 measured samples for at least 100 samples **per** alternating filter
command; summaries retain insertion and deletion separately. Eight total
commands cover a full compass cycle. `make benchmark-popup-smoke` uses only six
measured samples plus two warmups at 100 and 2,500 source rows (exercising
the equal-count display-cap boundary); its p99 is a protocol diagnostic, not a
credible tail-latency estimate. Linux/macOS 31.1 CI executes both load modes
and retains raw JSON artifacts for 30 days. No timing threshold is enforced,
and a passing smoke alone does not establish a performance baseline.

## Collecting full native profiles in CI

The separate **Native popup profile** workflow runs on benchmark-code pull
requests (excluding retained result files) and can also be launched manually through GitHub Actions. It measures
100, 1,000 and 10,000 source rows with 10 warmups and 200 measured commands per
case on Linux/macOS Emacs 31.1. Source and fresh-bytecode modes run sequentially
on the same runner; each artifact contains both raw reports and their complete
source/runtime provenance. Artifacts expire after 90 days, so retain selected
published profiles under `bench/results` together with the workflow run and
artifact identities. Merely adding this workflow does not publish numbers.

It enforces correctness/protocol completion and bounded process lifetime, not
latency thresholds. Hosted runners are shared infrastructure with uncontrolled
scheduling and CPU frequency. Cross-platform and source/bytecode differences
are observations on these runners, not universal speed ratios. For optimization
claims, run baseline and candidate on the same otherwise comparable runner and
retain both inputs and every sample. Package/runtime compatibility CI remains
independent and required.

## Comparing popup movement changes

The **Popup movement comparison** workflow checks out the PR base and candidate
on each Linux/macOS 31.1 runner, requires byte-identical measurement fixtures,
then measures baseline/candidate source followed by baseline/candidate bytecode.
It exercises navigation and compass movement at 100/10,000 rows with 10 warmups
and 200 measured commands each. Four raw reports per runner retain both source
identities, loaded definitions, counters and clocks; artifact retention is
90 days. A manual run accepts a baseline ref with the same fixture.

This paired order reduces hardware/configuration ambiguity, but does not remove
scheduling, frequency, warm-cache or run-order effects. There is no timing gate.
Retain selected paired raw data and qualify any claimed improvement; compatibility
and actual native state/cleanup tests remain independent required checks.

## Unsorted completion preparation

Use `--presentation popup --kinds filter-completion --completion-sort none`
to exercise provider metadata with no display sorter. The default remains
`identity`, preserving the original workload. Reports record `display_sort`
inside `provider_fixture`; do not compare differing policies as if identical.
The unsorted path still computes the full native projection, but only copies
the bounded displayed subset for decoration. A sorter may modify its entire
input, so its full candidate isolation remains necessary.

Native smoke runs both policies in source/bytecode at 100 and 2,500 rows, with
exact filtered/unfiltered candidate validation and required terminal paint.
Six measured commands validate the protocol; they are not a latency baseline.
For a full unsorted profile, use 200 samples, 10 warmups and 100/1,000/10,000 rows.
No before/after unsorted performance claim is established by this addition.

## Opt-in completion stage attribution

Add `--completion-stages` to a popup workload containing `filter-completion`.
This installs benchmark-only around advice after loaded-library verification;
package code is unchanged. Reports mark `completion_stages: true`. Do not treat
instrumented and uninstrumented runs as directly comparable latency pairs.
Advice, clock and counter overhead contributes to total command and PTY time
and allocation counters.

Each native completion edit records inclusive `projection_ms`,
`native_matching_ms` (the native completion-all-completions call),
`decoration_ms` and `publication_ms` (the existing-popup update), plus each
stage's call count. Matching is nested inside projection; actual table callbacks
are nested inside matching/projection too. Do not sum these overlapping clocks.
Projection includes metadata, boundaries, copying and deduplication; decoration
includes optional sorting, bounded copies, decoration and validation. Publication
includes toolkit update/render work. Final forced redisplay remains a separate,
possibly overlapping observation. These are wall times, including any GC.

Startup, initial popup creation and post-timing validation do not count as stage
calls. Every measured completion command must call each stage exactly once;
other cases record zero. Missing/nonfinite/negative timings, missing calls or
matching time larger than inclusive projection reject the report. Error paths
preserve the original exception and cannot produce a successful benchmark.

The full native profile now runs both identity and absent display sorters on
Linux/macOS, with stage attribution in source/bytecode modes. Each job retains
its own raw reports for 90 days. These are current profiles, not a matched
before/after proof for the earlier bounded-copy change. The published original
baseline remains uninstrumented and immutable.
